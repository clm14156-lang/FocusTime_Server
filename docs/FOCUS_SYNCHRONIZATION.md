# 第五阶段：双向增量同步

更新：2026-11-03。沿用第四阶段的本地记录、上传队列、身份和设备会话，实现完成记录的下载、删除传播、稳定分页及账号隔离。目标、真实任务、屏蔽规则和其他设置继续留在本机。

## API 与版本

所有接口均需 Bearer 认证，账号和来源设备由服务器会话确定，响应禁止缓存。

| 方法 | 路径 | 内容 |
| --- | --- | --- |
| POST | `/api/v1/sync/focus-records/push` | 逐项 `upsert` 或 `delete`；最多 200 项；逐项返回状态与版本 |
| GET | `/api/v1/sync/focus-records/changes?cursor=...&limit=50` | `changes / nextCursor / hasMore`；首次不传 cursor |
| GET | `/api/v1/focus-records?cursor=...&limit=50` | 稳定历史快照；`items / nextCursor`，结束时 nextCursor 为 null |
| GET | `/api/v1/focus-records/{recordId}` | 当前账号单条未删除记录；删除后返回 404 |

分页 limit 为 1–200，实际页面还受约 350 KB 载荷预算限制，因此可能少于请求数量。分页顺序为服务器版本升序；客户端原有时间线按记录完成时间展示。历史列表当前不提供 from/to 过滤，时间筛选沿用客户端已有逻辑。

`delete` 保留固定 operationId、recordId，`record=null`。客户端删除操作的 baseRevision 固定为 null，避免迟到上传确认改变同一操作的请求摘要。接口允许可选正整数 baseRevision；完成历史采用删除优先策略，不以旧观察版本阻止删除。

## 稳定游标与迁移

迁移 `20261103095323_FocusBidirectionalSync` 新增 `focus.changes`。每次实际新增或删除记录，在同一账号事务中写入不可变变化快照、当前记录、收据及下一版本。变化表主键为 `(UserId, Revision)`，并有 `(UserId, RecordId, Revision)` 索引。

迁移将第四阶段已有记录按原版本回填，保留用户、会话和原记录 ID，不重新上传或重新编号。幂等迁移不会重复回填。

游标由服务器 HMAC 签名，绑定用户、查询用途、已读版本及当前分页上界。开始一轮读取时取得已提交的最高版本；后续页面固定这个上界。分页期间新增或删除的记录在下一轮出现，不会让尚未访问的旧快照消失。历史列表通过变化日志选取上界以内的最后状态，同样保持稳定快照。

增量页的 nextCursor 即使没有变化也会返回。客户端保存原字符串，不自行拼接或解析；`hasMore=true` 时继续当前轮，false 时下次使用该游标开始新一轮。篡改、跨用户或混用历史/增量游标返回 `400 invalid_sync_cursor`。

变化历史和墓碑本版不清理。业务删除使当前查询不可见，但保留墓碑及分页所需旧快照，不代表立即物理擦除。以后引入保留期限时需同时实现游标过期和完整恢复协议。

## 删除与重试

- 删除尚未上传的 ID 也会创建墓碑；迟到的首次上传不能复活它。
- 同 ID、同完成快照是重复成功；不同快照返回 `record_conflict`，原云端内容保留。
- 墓碑后的新 upsert 返回 `record_deleted`。旧 upsert 收据重试可以返回其原确认版本，但不修改墓碑或新增版本。
- 删除本地记录时，停止发送旧 upsert，原子写入可重试删除操作并隐藏本地历史；网络失败不恢复已删记录。
- 下载记录在本机删除后，缓存保留 local_deleted。分页重放的旧 upsert 不会使它重新出现。
- 服务器墓碑与本地游标一起提交，移除本账号相应本地完成记录并确认待删除操作；不重新提交一个云端删除。
- 删除目标同时登记当前账号及未归属可见记录的本地删除；仅当前账号有云端删除操作。其他账号的历史快照保留，可在其账号下使用快照显示已不存在的目标。

第四阶段 state=4 的延后删除队列在本地 v16 迁移时转为可发送，保留操作 ID。响应丢失后重复发送相同请求，服务器不生成重复记录或重复版本。迟到确认只作用于匹配的操作、账号和 API 地址，不能清除较新操作、另一账号数据或删除标记。

## 客户端存储与导入

SQLite 从 v15 升到 **v16**，复用原初始化器的迁移前备份，新增：

| 表 | 用途 |
| --- | --- |
| `focus_sync_progress` | 每个账号/API 绑定的原始游标、最后应用版本、是否还有下一页、最近拉取时间 |
| `focus_sync_remote` | 按绑定及记录 ID 保存的服务器快照、版本、墓碑、本地删除及冲突标记 |

专用导入 IPC 带 expectedCursor、nextCursor 和整页变化。服务器数据、墓碑与游标在同一本地事务提交；任何写入或版本顺序校验失败，整页回滚。只在预期游标仍匹配、账号仍为当前绑定时应用，进程中断后从原游标重试。

下载内容直接投影为现有 LocalFocusSession 及任务快照。不会调用“真实专注完成”保存流程，不标记本地任务完成，不重建目标或任务实体，不触发完成提示、音效或屏蔽执行。目标在当前设备不存在时，原统计和日历使用 TargetNameSnapshot 与任务快照显示。

相同 ID 的本地记录与云端内容不一致时，保留本地原记录，同时缓存云端版本并显示“需处理”；不自动合并任意字段。重复的同一服务器版本必须有相同内容，否则页面拒绝应用。

## 账号与地址隔离

归属继续固定在记录首次保存时。A 开始的专注在切到 B 后完成，仍属于 A；进行中的本机专注按原逻辑继续。已完成历史只显示未归属本地历史及当前账号/API 地址的记录，退出后隐藏账号历史。

账号变化时桌面先清除旧可见历史和本地绑定，再读取新绑定。正在下载的旧账号页面会被代际检查和本地当前绑定检查拒绝。队列、游标、缓存及本地历史分页 token 均按绑定隔离；即使两个账号使用同一 recordId，也不会串数据。

未登录历史仍需用户确认归属。目标、真实任务和规则本身仍按原 Windows 用户存储，不在本阶段重构成云端账号资源。这里的隔离面向正常客户端的数据访问，并不加密本地 SQLite 以对抗拥有相同 Windows 文件访问权限的程序。

API 地址参与绑定，切换地址不会把旧地址未确认队列自动发送给新地址。当前 A 可继续使用 localhost，B 使用局域网 HTTPS；两者凭服务器账号同步。各机凭证仍由 Desktop 的 DPAPI 存储，令牌不经 IPC 发送给本地服务。

## 调度与游标恢复

沿用每 15 秒检查和“立即同步 / 重试”，每轮发送一批上传/删除，再读取最多 8 个增量页面，剩余页面在下轮继续。网络请求不持有本地 SQLite 事务或服务业务锁。上传失败继续持久化退避；下载失败保留原游标，后续检查继续读取。

客户端只在服务器明确返回 invalid_sync_cursor 时，每轮最多重置一次当前账号下载进度，并重新读取完整变化历史。重置不删除缓存、未上传记录、固定操作 ID 或本地删除标记；重放按版本去重。一般断网和服务异常不会重置游标。数据库从旧备份恢复导致版本倒退等恢复策略仍需部署阶段验证。

## 本地 IPC 历史分页

上传及下载页面都限制字节大小，客户端还核对下载映射后的 IPC 大小，必要时减小 HTTP 页面。

原 GetState 的 1 MiB 帧限制保持不变。完整历史超过传输预算时，服务返回带 token 的轻量状态，保留活动专注和最近完成结果；历史通过专用只读分页传输。Desktop 的 NamedPipeIpcClient 对状态、普通修改及强制专注结果重组完整历史后再交给原 ViewModel，统计不会只计算某一页。分页事件也先补全再发布，避免用临时部分数据替换完整历史。

历史页每页至多 50 条，并限制字节数。内存快照有界保存；账号变化即失效，Agent 无权读取这些页面。快照过期会有界重读，不发布不完整结果。仍需关注大量本机目标/规则或单条异常超大本地记录本身的帧上限，这不属于已实现的历史分页范围。

## 运行和验收

后端先执行新迁移，再启动。Windows 客户端需配套更新 **Desktop、Service、Agent**；新服务首次运行会备份并迁移本地数据库。当前运行的旧客户端进程不会因源码修改而自动升级，完成现有专注后按原流程配套重启。

不支持将旧 Desktop 与新 Service 混用，尤其是历史分页的完整性依赖新客户端重组。回退旧服务时使用迁移前备份，不直接让旧版本读取 v16 数据库。

客户端实际修改保存在独立 windowBlocked01 项目，并导出 `integrations/windowBlocked01/stage5-bidirectional.patch`，基于第四阶段后的客户端代码。局域网启动配置补丁独立保留，不混入业务同步补丁。

具体测试、构建产物和剩余人工验收见 [第五阶段验证记录](STAGE5_VALIDATION.md)。会员、权益及离线会员凭证仍属于第六阶段。
